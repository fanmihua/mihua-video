# 写稿：选题、开头、说法

什么时候读：定选题、写口播稿、稿子给用户看之前自查。
稿子文件的格式（`显示 | 读法`、`<pause>`、`[小红书]`）和换话题的停顿，见 `audio.md` › script.md 写法、› 节奏。写完照 › 7 跑 `copy_check.py`、过一遍清单。

## 0. 先分清这支视频用在哪
视频有两种场景：**对外的自媒体视频**（小红书、抖音、B 站单发）和**教程**（成套的教程、配合文字版看的讲解）。画面风格、品牌层两种一样，**讲故事的方式不同**。
- 开工前先确定是哪一种：内容确认单里写了就照写的；没写或拿不准，**先问用户**，不自己猜。
- 两种的区别：

  | | 自媒体 | 教程 |
  |---|---|---|
  | 选题、结构 | 选题三问，从观众的痛点出发（› 1）；一条讲一个点 | **也从学的人要解决的问题出发**：先讲这能帮你解决什么、在什么场景用，再给一张全局图讲各部分怎么连起来，最后按场景讲怎么用；讲一个功能，讲它替学的人省掉了什么麻烦，不报数字显摆（讲自动检查不说检查了几百项，说「用 AI 做界面，最担心做得对不对、还得自己一项项走查——这一步也交给 AI」）；不按「包含什么」逐项介绍，看的人在意的是这东西能替他解决什么；有配套文字版的，标题和说法跟文字版对上 |
  | 开头 | 第一句给结果或痛点，3 秒内放结果画面（› 2） | 也守黄金三秒：第一句就是学的人的痛点，画面同时在演，5 秒内给结果；问候放在后面。口吻是老师讲课，不夸张、不夸大，不用悬念式钩子 |
  | 段与段 | 滑梯效应 | 也用滑梯效应：每一段最后一句把人拉到下一段（「这一步做完，还差一件事」→ 下一段讲那件事）；有下一节的，结尾只说下一节讲什么、不给答案，也不用问句（Joseph Sugarman：第一句的目的是让人读第二句） |
  | 说法 | 口语、像本人平时说话（› 4） | 像老师讲课：不口语（不加语气词、梗、俚语），也不书面腔（不用「进行」「实现」「此外」，不用「把取值推到边界」这类书面比喻）；短句，写给耳朵听；讲清楚它是做什么用的、为什么要有，具体数值放画面上；术语照用，第一次出现时一句话说清是什么；有文字版的，沿用它定过的标题和说法 |
  | 标题、封面 | 具体的东西 + 痛点或反差（`cover.md`） | 用本来的名字，直接说这一节讲什么（› 5 比喻那条） |
  | 链接、地址 | 不露（`materials.md` › 安全） | 可以露（同上） |

- **教程不用问句**：口播里不自问自答、不用设问，直接说结论或担心——「要全背下来吗？不用」→「不用一下子全记住」；「插件和 MCP 是一个东西吗？」→「插件和 MCP，最容易弄混」；「该怎么跟它配合？」→「下一节，讲怎么跟它配合」。为什么：老师讲课自己问自己，听着像卖关子。`copy_check.py --scene tutorial` 会把问句标成「要改」。
- **教程写完逐段自查三句**：① 这段回答的是学的人哪个担心或需要（看不懂代码、怕做错、不知道怎么接自己的项目）？② 是不是在介绍我们做了什么、包含什么、数字有多大？是就改成「你担心 X → 没关系，这样做 → 结果」；③ 要做的事有没有落到「跟 AI 怎么说」，让人看完能去试？用户指出一处，先提炼成原则，把全篇同类的地方都改掉，再给用户看。
  - 例：原稿逐项介绍「文件夹里每部分放在哪、照哪份说明、怎么检查」→ 改成「这些代码看不懂没关系，可以直接交给 AI 去分析，你要知道的只是怎么跟它说」。
- 两种都要：直接给结果、不写转折句，不念代码名，不要 AI 腔（› 4）；说法和官方一致（› 3）；讲清楚（› 5）；不对外的内容不出现（› 6）；换话题停够（`audio.md` › 节奏）。

教程口吻：写给耳朵听，像跟朋友讲但不随便，术语准确；书面腔、数值太细的句子改成短句，讲清这一步为什么要有、用来排除什么，读起来像课本的内容放到画面或文字版。

为什么：场景弄错了，口播要整版重写。两种画面风格一样，只是讲故事的方式不同。

## 1. 选题三问（自媒体）
每支自媒体视频写稿前过一遍，内容确认时再确认一次（教程照 › 0）：
1. 观众手上正在做这件事吗？
2. 能说出他们踩过的坑吗？
3. 开头三秒能放出结果吗？

从观众的痛点出发，不从「我们做了什么」出发；有一问答不上，先改选题和切入点，再写稿。
- 对：从观众正在踩的坑出发的题目（比如「规范都写了，AI 做出来的界面还是不对」），三问都答得上，开头直接放结果。
- 错：从「我们做了什么」出发的题目，第十几秒才抛出问题。

为什么：信息流里的人刷到就决定看不看，题目和开头戳不中，后面讲得再好也没人看到。

## 2. 开头 3 秒（自媒体；教程照 › 0）
- 第一句就是这支的结果或观众的痛点，画面同时放结果（画面怎么做见 `motion-language.md` › 4. 章节结构）。
- 不用纯音乐开头：配音、转写的 `--intro` 写 0–0.5（脚本默认值还是 1.4，命令里要写上）。
- 不先打招呼；要打就在钩子之后一句带过（「我是 ×××」）。
- 不先讲「上一期」的来由；要提，放在钩子后面。
- 不念目录：导航可以出现，口播不一个个列章节。

为什么：人在开头几秒就决定留不留下，纯音乐、招呼、来由、目录都是让人等。

## 3. 说法和官方一致（所有视频都要遵守）
- 讲到的工具、框架、平台，每条说法都去读这家官方文档的原文（官网打不开就用浏览器读，读到原文为止）；官方没写到的细节对源码核实（比如 `node_modules` 里的源码），也要实测。
- 交接里列一张「官方原文 → 稿子里的说法 → 一致吗」，错的先改稿，再合成配音。
- 名词用官方原名：官方叫 Seed Token 就说 Seed Token，不自己起个中文名当成官方叫法。
- 不能说出和官方相反、或者让照官方文档做的人对不上的话：只讲了「在外层改不生效」，就要补上「照官方的做法在最外层改是生效的」。
- 拿不准的不说。
- **不夸大，只说做到并验证过的**：没验证过的说成「一种可行的做法」「可以照着它去试」「接好的标准是……」，不说「就是来解决」「就能」「只要一句就行」「AI 会做好」；验证过的要说清范围（在哪些情况下验证过）。写完搜一遍「就能」「只要」「一定」「解决」「不会」「都」，每处问：这件事真的做到、验证过吗？

为什么：可信很重要；讲技术的视频说错一处，内行一眼就看出来。

## 4. 像本人说话
- 第一条只管自媒体（教程的说法照 › 0）；后面几条两种都要。
- 口语、短句、第一人称；不写书面语，不写「家人们」「干货满满」「绝绝子」这类营销腔。语气参考用户自己以前的口播（自己录的视频转写出来的那份 `timing/film.json`）。
- 不要 AI 腔、翻译腔：比如「这个数是怎么一站一站走过去的」「有了这条路，就能说清」。
- 不硬造比喻词：流程分几段就说「几步」「第一步」，不说「几站」「第一站」。
- **直接给结果，不写转折句**：
  - 不写先说一个不对的、再翻过来给答案的句式：「不是…而是…」「我不会先…而是…」「但…其实是…」「…就不像…了」。
  - 直接说：「镜头怎么选，就看这句话想干什么」；效果也正着说：「镜头一路走过去，一镜到底」，不说「就不像翻 PPT 了」。
  - 写完搜一遍「不是」「而是」「但」「不像」，每一处问：删掉前半句、直接说后半句行不行。
  - 讲改前、改后的对比不算转折，那是内容本身，照常讲。
  - 为什么：观众得先弄懂一个被否定的说法才听到答案，很累。
- **口播不念代码名**：`className`、`props`、`px` 这类，口播说中文意思（「样式名」「组件的属性」「像素」），英文只出现在画面上。产品名、文件名（Ant Design、Design.md、Markdown、React、Vue）照念。为什么：配音读出来别扭，观众也听不懂。
- **动词要对上做的人**：设计师「做」设计、「定」规范；组件库「实现」页面；AI「生成」「翻译」；代码、文档才是「写」的。不用随口的近似词（写设计、画页面、组件库读不懂）。写完把每个动词问一句：这个动作是谁做的，真的是这么做的吗？
- 写完每句问一下：用户平时会这么说吗？

## 5. 讲清楚
- **按观众的水平选讲什么**：挑知识点前先问一句「观众会不会已经懂」，观众已经懂的（压缩包、后缀名）不讲；新词一句话说清，能用观众熟悉的东西类比就用（观众是设计师，就用 Figma 类比）。
- **讲「怎么解决」不跳步**：一步一步说——问题是怎么来的 → 办法是什么 → 用了办法以后发生了什么。每个「所以」「这样就」前面问一句：前后两种情况各自怎么拿到这个值，观众听到了吗？没听到就补一句；这种两步对比，画面也画成并排的两步。
  - 例：原稿讲完原因，直接跳到「所以规范里单独写了一项」，看的人不知道这一项和刚才的问题有什么关系。改成三步：没交给它时它自己推 → 规范里本来就有这一项 → 交过去以后它就不推了，直接用。
- **从看得见的具体差异讲起，再上升到概念**：先讲颜色写法、尺寸写法、图标写法这种一眼看得出的不同，不一上来就讲数值和概念。
- **举例覆盖不同做法**（Figma、AI 生成、AI 翻译……），不只举一种人的做法。
- **比喻只用在讲原理的地方**：目录、章节导航、片头「这一支看……」、下一节预告、标题和封面，都用本来的名字，直接说这一支讲的东西；比喻（比如片场这类插画世界）只出现在讲「为什么」的那几段，那几段的画面才用插画场景。为什么：观众先要知道讲的是什么，比喻是帮他听懂，不是给内容换名字。
- **讲技术不砍内容，先把节奏和说法弄顺**：用户说「太绕、看不懂」时，先查换话题停够没有（`audio.md` › 节奏）、口播念没念代码名、有没有 AI 腔，再考虑删；要删先出一小段给用户对比，别整支重做。为什么：删成只留主线的短版，看的人往往反而想要回原来的完整版。
  - 适用范围：这条和「时长不设限」只管深度教程和长版；60–90 秒的短版一条只讲一个点。

## 6. 不对外的内容
- 做视频的人自己的私事、个人担心、商业决定和计划、私下商量「讲不讲」的内容、还没发布的东西：一律不进口播、画面、字幕和封面；不当例子，也不说「这件事先不讲」。
- 跟用户本人经历、想法有关的改稿细节（比如 AI 初稿把用户的视角写错了）也不举例，只讲规则本身。
- 能对外的：方法、原则、流程、分工，以及已经发布过的内容。拿不准先问用户。
- 每支把具体的条目写进 `素材/内容确认单.md` › 绝不出现。

为什么：这些是制作过程里的事，不是观众要看的内容。

## 7. 写完扫一遍
稿子给用户看之前，先跑脚本（口播稿、Markdown 都认；工程里 `tools/` 下也有一份）：
```bash
python3 <skill>/assets/kit/tools/copy_check.py 稿子.md --scene selfmedia|tutorial
```
自媒体用 `selfmedia`，教程用 `tutorial`。「要改」是硬规则（转折句、营销腔，教程还有问句），改到没有；「留意」逐处看上下文再定。然后过清单：
- [ ] 稿子开头的注释（`<!-- -->`，不会被念）写了「看完，你能……」和「写给谁（一个具体的人）」；不服务这句话的段落删掉，或挪去画面、文字版
- [ ] 每段说得出一句结论；可有可无的字、句、段删掉（不带信息的形容词、过渡词、多余的「的」），删完主语、动作、对象还在
- [ ] 换回简单动词和日常词：「对布局进行调整」→「调整布局」；一句不超过三个「的」；不用「当……的时候」「作为……」「通过……来」、被动句
- [ ] 没有 AI 腔：凑数的三段式、句尾挂一句意义（「这体现了」）、空洞大词（赋能、打造、闭环）、模糊归因（「业内普遍认为」，说不出是谁就删）
- [ ] 一句一个新东西；超过三步的清单不念，口播说「一共五步，都在画面上」，只讲最容易出错的那一步
- [ ] 画面看得见的不念，口播补「为什么、省了什么」；精确数字放画面
- [ ] 替配音排雷：已 → 已经，若 → 如果；口播里不放括号、斜杠、破折号；「该组件」「其」换成名字
- [ ] 念出声（或用克隆声音听一遍）：一口气念不完、重音不对、绊嘴的句子拆开

教程再看：
- [ ] › 0 的自查三句逐段过了；有路标句（开头「这一节讲三件事」，每段开头「第二件事：……」，结尾用同样的词收）
- [ ] 新名词先给样子再给名字：「从屏幕右边滑出来的那块面板，叫抽屉」
- [ ] 至少一处把学的人的担心说出来再给答案（「你可能担心：……」停一拍，再说结果），代替转折句
- [ ] 结尾放一个最清楚的前后对比和「做成了」的画面，加一句回顾

自媒体再看：
- [ ] 封面字先定了（2–3 版跟稿子一起给用户），第一句照着它兑现；第二、三句回答「跟我有什么关系」
- [ ] 反差用两个事实并排；损失写具体（「交给开发的图标线条会变粗」），不写「崩溃」「焦虑」这类情绪词
